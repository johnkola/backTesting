Project docs live in `docs/GETTING-STARTED.md` (the operating path end to end) and `README.md` (roadmap, model cache, storage, deployment). The design the project implements lives in `docs/readonly-doc/` — `Architecture.md`, `Design Notes.md`, `Features.md` — and is the authority on what this system is for. Start with the first two, then the design set. Before changing anything, read the working rules at the top of `AGENTS.md`.

`docs/readonly-doc/` is read-only in the literal sense: the author maintains those three files by hand and nothing in this repo may write to them. Read them, cite them, never edit them. It supersedes `docs/reference/qqq-backtesting-model/`, which is an earlier revision of the same three documents and is kept only for history — its `Design.md` still fits normalization statistics on each feature's full history, where the current text fits them on the training window only, per walk-forward fold, so the old wording describes a leak. Do not quote it as current.

**Which doc gets a new fact.** The two project docs do not overlap by design, and a fact belongs in exactly one of them; the other links to it. `docs/GETTING-STARTED.md` owns the operating path and nothing else — it is the only end-to-end walkthrough, and it stays short by linking. `README.md` owns the operator surface: what to type and what to configure (CLI flags, API routes, env vars, recovery recipes, the roadmap).

There is no project-owned architecture doc. The root `ARCHITECTURE.md` was deleted when `docs/readonly-doc/` became the design set, and `docs/readonly-doc/Architecture.md` is not a replacement for it — it describes the QQQ system, not this codebase, and it is not ours to extend. So the code side of a fact — why something is shaped this way, which invariants are load-bearing, what a change must not break — goes in the code: a module or class comment at the top of the file that owns the decision, and the commit message that made it. When a topic has both an operator and a code side — the model cache, aggregation, compression, the drop-folder ingest — `README.md` takes the operator half and the owning module takes the rest, rather than it being told twice.

Standalone tools keep their own README beside the code rather than a section in `README.md` — `tools/datagen/README.md` and `postman/README.md` are the current ones. (`web/client/README.md` is the unedited Vite template and says nothing about this project.) A project doc should point at such a README, never restate it.

`docs/DESIGN-GAPS.md`, `docs/DOC-REVIEW.md` and `docs/UI-REVIEW.md` are rolling trackers, not project docs: they are deliberately absent from the `DOCS` registry in `web/api/docsRegistry.js` and do not render at `/docs`. `docs/DESIGN-GAPS.md` lists what the design asks for that the code does not do yet; the other two are review trackers. `docs/REQUIREMENTS-CONSOLIDATED.md` (one numbered list of the requirements, merged from the design set and the trackers; a draft the author is reviewing) and `docs/QUESTIONS-FOR-JOHN.md` (the open decisions he has to make) sit beside them and are not in the registry either. `docs/DATA-SOURCES-RESEARCH.md` is the data-source inventory for the feature table (free and paid sources per feature at daily, hourly and 30-minute bars, with date ranges), exported from the author's research doc; it is reference material, not in the registry, and `docs/readonly-doc/Features.md` stays the authority on the feature list itself. `docs/reference/r-d/` holds the oldest copies of the design set (`DESIGN.md`, `FEATURES.md`, `ARCHITECTURE.md` and the 2026-10-18 draft), moved here from the author's R-D repo so every doc for this app is in one repo; like `docs/reference/qqq-backtesting-model/` they are history only and must not be quoted as current.

`AGENTS.md` is the step-by-step review list: the app's steps from a running stack to the held-out test, what has to be true for each to count as done, and a review table we fill in one step at a time. It also holds the author's working rules for agents, and the build steps: for each open gap in `docs/DESIGN-GAPS.md` that is being closed, what has to be true before it is done. It owns the definitions of done and nothing else: the evidence and the plan for a gap stay in `docs/DESIGN-GAPS.md`, and how to run a step stays in `README.md` and `docs/GETTING-STARTED.md`, and it links there. Like the trackers, it is not in the `DOCS` registry.

Note: the `/architecture` and `/claude` routes on the API are 301 redirects to the client's `/docs/qqq-architecture` — the only Architecture document left, and there is no separate Claude-facing doc page. Those targets are checked against the registry in `docsRegistry.test.js`, because a redirect to a slug the registry does not know is a 301 into a 404. The docs render inside the React client at `/docs`; the API serves them as JSON from `/api/docs`.
