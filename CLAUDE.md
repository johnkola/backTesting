Project docs live in `GETTING-STARTED.md` (the operating path end to end) and `README.md` (roadmap, model cache, storage, deployment). The design the project implements lives in `read-only-doc/` — `Architecture.md`, `Design Notes.md`, `Features.md` — and is the authority on what this system is for. Start with the first two, then the design set.

`read-only-doc/` is read-only in the literal sense: the author maintains those three files by hand and nothing in this repo may write to them. Read them, cite them, never edit them. It supersedes `reference/qqq-backtesting-model/`, which is an earlier revision of the same three documents and is kept only for history — its `Design.md` still fits normalization statistics on each feature's full history, where the current text fits them on the training window only, per walk-forward fold, so the old wording describes a leak. Do not quote it as current.

**Which doc gets a new fact.** The two project docs do not overlap by design, and a fact belongs in exactly one of them; the other links to it. `GETTING-STARTED.md` owns the operating path and nothing else — it is the only end-to-end walkthrough, and it stays short by linking. `README.md` owns the operator surface: what to type and what to configure (CLI flags, API routes, env vars, recovery recipes, the roadmap).

There is no project-owned architecture doc. The root `ARCHITECTURE.md` was deleted when `read-only-doc/` became the design set, and `read-only-doc/Architecture.md` is not a replacement for it — it describes the QQQ system, not this codebase, and it is not ours to extend. So the code side of a fact — why something is shaped this way, which invariants are load-bearing, what a change must not break — goes in the code: a module or class comment at the top of the file that owns the decision, and the commit message that made it. When a topic has both an operator and a code side — the model cache, aggregation, compression, the drop-folder ingest — `README.md` takes the operator half and the owning module takes the rest, rather than it being told twice.

Standalone tools keep their own README beside the code rather than a section in `README.md` — `tools/datagen/README.md` is the current one. A project doc should point at such a README, never restate it.

`DOC-REVIEW.md` and `UI-REVIEW.md` are rolling review trackers, not project docs: they are deliberately absent from the `DOCS` registry in `docsRegistry.js` and do not render at `/docs`.

Note: the `/architecture` and `/claude` routes on the API are 301 redirects to the client's `/docs/qqq-architecture` — the only Architecture document left, and there is no separate Claude-facing doc page. Those targets are checked against the registry in `docsRegistry.test.js`, because a redirect to a slug the registry does not know is a 301 into a 404. The docs render inside the React client at `/docs`; the API serves them as JSON from `/api/docs`.
